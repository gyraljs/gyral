# ADR 0012 — Server rendering and hydration

Status: **accepted** (2026-10-04). Beads: gyral-4k7.1 (`@gyral/ssr`), gyral-14f.17 (isomorphic
example). Follows the lit-web-apps skill: `@lit-labs/ssr`, Declarative Shadow DOM (DSD),
hydration support imported first, data fetched in route handlers.

## Decisions

### 1. On the server, `init(props)` renders; commands never run

Lit's server renderer runs only `constructor`, `willUpdate` and `render`. A Gyral element
computes `init(props)` and renders the view. Commands returned by `init` are **dropped on the
server**: there is no interpreter, no `connectedCallback`, no timers. All async work belongs
in the route handler, which passes results down as props.

### 2. Hydration seed: one attribute per element

In `willUpdate` on the server, each Gyral element writes
`data-gyral-seed='{"state": …, "props": {…}}'` on its host:

- `state` is the state the server rendered.
- `props` holds only props that an attribute cannot carry, such as property bindings
  (`.items=${data}`). Attribute-backed props already travel as attributes.

The renderer HTML-escapes attribute values, so hostile strings in state cannot break out (a
test checks this). Script-context escaping (`</script>`) is not needed because the seed is
never inside a `<script>`.

Considered and rejected: a page-level `__DATA__` script. It needs a key per element and an
ordering contract, and nested elements that the server rendered but nobody serialized would
still mismatch. A per-element seed is local, needs no registry, and covers nested components
automatically.

**Constraint:** the state and props of server-rendered components must be JSON data (no Maps,
Dates or class instances). This is the same discipline as commands being data (ADR 0006).

### 3. On the client: resume from the seed, then start `init`'s commands after hydration

When an element connects with a seed, it reads the seed and removes the attribute. It then:

1. Restores seeded props that are still `undefined` (props a hydrating parent already set
   win).
2. Uses the seeded state as its model.
3. Re-runs `init(props)` **for its commands only**, and starts them **after the first
   (hydrating) update completes**.

Why after hydration: drivers can answer synchronously. The router's `listen()` emits the
current location immediately. If that message landed before the hydrating render, state would
differ from the server markup and Lit would fail with "Hydration value mismatch". Starting
commands later means hydration always matches. A different URL (or any other driver answer)
then arrives as an ordinary update. Both cases are tested.

One code path serves CSR and SSR: `init` is the single place that says which subscriptions a
component needs. To avoid re-fetching data the server already provided, make the fetch
conditional on the props (`props.products ? s : [s, [load()]]`). That decision is identical
on both sides.

### 4. `@gyral/ssr`: runtime-agnostic rendering

- `page({ title, body, description?, head?, scripts?, lang?, dir? })` is the server-only
  document shell. It is never hydrated. `body` is a normal `lit` template.
- `renderPage(options, init?)` returns a streaming `Response`. It also offers
  `renderToStream(value)` and `renderToString(value)`.
- `serverHtml` is for server-only head content.
- `@gyral/ssr/hydrate` is the side-effect import that must come **first** in a client entry.
- These return web `Response`/`ReadableStream`, so Hono, Deno, Bun or a Service Worker can
  serve them. Hono is used in the example, not required by the package.
- `@lit-labs/ssr` is reached only through `packages/ssr/src/internal/lit.ts` (ADR 0005),
  which ESLint enforces.

### 5. Routes and data

The server matches with the same `routes()` table as the client (`@gyral/router` matching is
pure). The route handler does all async work and passes results as props. The http driver's
`baseUrl` defaults to `location.href` **at request time**, which never happens on the server
(decision 1). Server-side data loading uses whatever client the handler likes, not the
driver.

## Consequences and limits

- Server-rendered pages are readable with JavaScript disabled (DSD). This is verified in the
  isomorphic example.
- Tests: Node renders (DSD output, seed contents, escaping, no commands on the server). A
  golden file of the real server output (`examples/isomorphic/test/fixtures/*.html`, updated
  with `pnpm test -u`) feeds browser hydration tests. Those tests assert the same DOM nodes,
  no mismatch, a consumed seed, and interactivity.
- Not yet: SSG/prerender script, a production build/serve script for the example,
  `defer-hydration` islands, updating `document.title` on client navigation.
- The ADR 0008 server half (`formAction`) uses this seed: the rejected state rendered on the
  server is what the client resumes from. See ADR 0008, "Server half".

## Addendum: boolean form state in server-rendered views (gyral-4k7.9, 2026-10-04)

Lit SSR serializes a **property** binding as an attribute: `.checked=${false}` becomes
`checked="false"`, and any `checked` attribute checks the box. gyral-shop shipped every no-JS
filter checkbox pre-ticked because of this. Rules:

- Bind boolean form state as `?checked=${liveBoolean(value)}` (also `?selected`, `?open`,
  `?indeterminate`). On the server, `liveBoolean` renders the bare attribute or omits it. In
  the browser it also sets the property of the same name, so the control follows the model
  even after the user has changed it (a plain `?checked` stops controlling `checked` once the
  box has been clicked).
- ESLint (`no-restricted-syntax` in `eslint.config.js`) rejects `.checked=`, `.selected=`,
  `.open=`, `.indeterminate=` and `.defaultChecked=` bindings in `html`/`serverHtml`
  templates. Apps should copy the rule.
- Tests: `packages/ssr/test/live-boolean.node.test.ts` (server markup, plus a test pinning the
  Lit behaviour) and `packages/core/test/live-boolean.test.ts` (live property).

## Addendum: the `Hydrated` message (gyral-czi.23, 2026-10-04)

Progressive enhancement means rendering the no-JS UI on the server and in the first client
render (hydration must match), then switching to the enhanced UI. gyral-shop's buy box faked
"now live" with a `delay(0)` init command. Instead, every client-side instance gets the
framework message `Hydrated { serverRendered }` once, after its first render has completed:

```ts
update: {
  Hydrated: (s) => ({ ...s, enhanced: true });
} // optional reducer
```

- **Sent to client-only instances too** (`serverRendered: false`). "The component is live in the
  browser" is what enhancement code needs either way. The flag says whether it resumed from a
  hydration seed.
- **Sent once per instance**, not again on reconnect. Never on the server.
- **Order:** `Hydrated` first, then init's deferred commands (on the seed path). Both happen
  after the hydrating update, so they start a fresh render.
- The reducer is optional. Components without it pay nothing and get no warning.

## Addendum: nested components and `defer-hydration` (2026-10-04)

A Gyral component server-rendered inside another component's shadow root gets
`defer-hydration` (Lit SSR adds it to every custom element inside a host's DSD), so it doesn't
hydrate before its parent. Lit's hydrate support then skips `connectedCallback` while the
attribute is present, and connects the element by calling **LitElement's own**
`connectedCallback` once the parent's hydration removes it. Gyral's override was bypassed
both times: the first time it crashed (`renderRoot` was not created yet), the second time it
never ran, so intents were never wired (found by gyral-shop's mini-cart in the header).

`define()` now skips its connect work while the element is deferred (only when hydrate support
is loaded: `defer-hydration` is in `observedAttributes`), and finishes it in
`attributeChangedCallback` when `defer-hydration` is removed. Seeded state, init's deferred
commands and `Hydrated` then run as for a top-level component. Tested end to end:
`packages/ssr/test/nested.node.test.ts` writes the server markup and
`nested-hydration.test.ts` hydrates it and clicks the nested child.

## Addendum: CSP

Hydration seeds need no inline-script allowance (`data-gyral-seed` is an attribute; the store
seed is `type="application/json"`, which CSP doesn't execute). Declarative Shadow DOM
`<style>` elements do require `style-src 'unsafe-inline'` (or hashes).

# ADR 0012 — Server rendering and hydration

Status: **accepted** (2026-10-04). Beads: gyral-4k7.1 (`@gyral/ssr`), gyral-14f.17 (isomorphic
example). Follows the lit-web-apps skill: `@lit-labs/ssr`, Declarative Shadow DOM (DSD),
hydration support imported first, data fetched in route handlers.

> **Superseded in part by [ADR 0018](0018-view-layer.md)** (2026-10-06, shipped in 0.3.0): the server renderer, hydration, form-state bindings and islands are specified in [view/06-server.md](view/06-server.md) and [view/07-hydration.md](view/07-hydration.md); the Lit workarounds recorded here go away. Lit-specific text below describes 0.2.x.

## Decisions

### 1. On the server, `init(props)` renders; commands never run

Lit's server renderer runs only `constructor`, `willUpdate` and `render`. A Gyral element
computes `init(props)` and renders the view. Commands returned by `init` are **dropped on the
server**: there is no interpreter, no `connectedCallback`, no timers. All async work belongs
in the route handler, which passes results down as props.

### 2. Hydration seed: one attribute per element

In `willUpdate` on the server, each Gyral element writes
`data-gyral-seed='{"state": …, "props": {…}}'` on its host:

- `state` is the state the server rendered.
- `props` holds only props that an attribute cannot carry, such as property bindings
  (`.items=${data}`). Attribute-backed props already travel as attributes.

The renderer HTML-escapes attribute values, so hostile strings in state cannot break out (a
test checks this). Script-context escaping (`</script>`) is not needed because the seed is
never inside a `<script>`.

Considered and rejected: a page-level `__DATA__` script. It needs a key per element and an
ordering contract, and nested elements that the server rendered but nobody serialized would
still mismatch. A per-element seed is local, needs no registry, and covers nested components
automatically.

**Constraint:** the state and props of server-rendered components must be JSON data (no Maps,
Dates or class instances). This is the same discipline as commands being data (ADR 0006).

### 3. On the client: resume from the seed, then start `init`'s commands after hydration

When an element connects with a seed, it reads the seed and removes the attribute. It then:

1. Restores seeded props that are still `undefined` (props a hydrating parent already set
   win).
2. Uses the seeded state as its model.
3. Re-runs `init(props)` **for its commands only**, and starts them **after the first
   (hydrating) update completes**.

Why after hydration: drivers can answer synchronously. The router's `listen()` emits the
current location immediately. If that message landed before the hydrating render, state would
differ from the server markup and Lit would fail with "Hydration value mismatch". Starting
commands later means hydration always matches. A different URL (or any other driver answer)
then arrives as an ordinary update. Both cases are tested.

One code path serves CSR and SSR: `init` is the single place that says which subscriptions a
component needs. To avoid re-fetching data the server already provided, make the fetch
conditional on the props (`props.products ? s : [s, [load()]]`). That decision is identical
on both sides.

### 4. `@gyral/ssr`: runtime-agnostic rendering

- `page({ title, body, description?, head?, scripts?, lang?, dir? })` is the server-only
  document shell. It is never hydrated. `body` is a normal `lit` template.
- `renderPage(options, init?)` returns a streaming `Response`. It also offers
  `renderToStream(value)` and `renderToString(value)`.
- `serverHtml` is for server-only head content.
- `@gyral/ssr/hydrate` is the side-effect import that must come **first** in a client entry.
- These return web `Response`/`ReadableStream`, so Hono, Deno, Bun or a Service Worker can
  serve them. Hono is used in the example, not required by the package.
- `@lit-labs/ssr` is reached only through `packages/ssr/src/internal/lit.ts` (ADR 0005),
  which ESLint enforces.

### 5. Routes and data

The server matches with the same `routes()` table as the client (`@gyral/router` matching is
pure). The route handler does all async work and passes results as props. The http driver's
`baseUrl` defaults to `location.href` **at request time**, which never happens on the server
(decision 1). Server-side data loading uses whatever client the handler likes, not the
driver.

## Consequences and limits

- Server-rendered pages are readable with JavaScript disabled (DSD). This is verified in the
  isomorphic example.
- Tests: Node renders (DSD output, seed contents, escaping, no commands on the server). A
  golden file of the real server output (`examples/isomorphic/test/fixtures/*.html`, updated
  with `pnpm test -u`) feeds browser hydration tests. Those tests assert the same DOM nodes,
  no mismatch, a consumed seed, and interactivity. Since 0.3.1 (gyral-dyn.8) a browser test can
  also get server markup on demand: `renderOnServer` from `@gyral/testing/vitest` is a Vitest
  browser command that renders a module's export with `@gyral/core/server` in Vitest's Node
  process (see ADR 0006, "Server-rendered page tests"). Golden files stay the choice for whole
  server stacks and reviewed markup.
- Not yet: SSG/prerender script, a production build/serve script for the example,
  `defer-hydration` islands, updating `document.title` on client navigation.
- The ADR 0008 server half (`formAction`) uses this seed: the rejected state rendered on the
  server is what the client resumes from. See ADR 0008, "Server half".

## Addendum: boolean form state in server-rendered views (gyral-4k7.9, 2026-10-04)

Lit SSR serializes a **property** binding as an attribute: `.checked=${false}` becomes
`checked="false"`, and any `checked` attribute checks the box. gyral-shop shipped every no-JS
filter checkbox pre-ticked because of this. Rules:

- Bind boolean form state as `?checked=${liveBoolean(value)}` (also `?selected`, `?open`,
  `?indeterminate`). On the server, `liveBoolean` renders the bare attribute or omits it. In
  the browser it also sets the property of the same name, so the control follows the model
  even after the user has changed it (a plain `?checked` stops controlling `checked` once the
  box has been clicked).
- ESLint (`no-restricted-syntax` in `eslint.config.js`) rejects `.checked=`, `.selected=`,
  `.open=`, `.indeterminate=` and `.defaultChecked=` bindings in `html`/`serverHtml`
  templates. Apps should copy the rule.
- Tests: `packages/ssr/test/live-boolean.node.test.ts` (server markup, plus a test pinning the
  Lit behaviour) and `packages/core/test/live-boolean.test.ts` (live property).

## Addendum: the `Hydrated` message (gyral-czi.23, 2026-10-04)

Progressive enhancement means rendering the no-JS UI on the server and in the first client
render (hydration must match), then switching to the enhanced UI. gyral-shop's buy box faked
"now live" with a `delay(0)` init command. Instead, every client-side instance gets the
framework message `Hydrated { serverRendered }` once, after its first render has completed:

```ts
update: {
  Hydrated: (s) => ({ ...s, enhanced: true });
} // optional reducer
```

- **Sent to client-only instances too** (`serverRendered: false`). "The component is live in the
  browser" is what enhancement code needs either way. The flag says whether it resumed from a
  hydration seed.
- **Sent once per instance**, not again on reconnect. Never on the server.
- **Order:** `Hydrated` first, then init's deferred commands (on the seed path). Both happen
  after the hydrating update, so they start a fresh render.
- The reducer is optional. Components without it pay nothing and get no warning.

## Addendum: nested components and `defer-hydration` (2026-10-04)

A Gyral component server-rendered inside another component's shadow root gets
`defer-hydration` (Lit SSR adds it to every custom element inside a host's DSD), so it doesn't
hydrate before its parent. Lit's hydrate support then skips `connectedCallback` while the
attribute is present, and connects the element by calling **LitElement's own**
`connectedCallback` once the parent's hydration removes it. Gyral's override was bypassed
both times: the first time it crashed (`renderRoot` was not created yet), the second time it
never ran, so intents were never wired (found by gyral-shop's mini-cart in the header).

`define()` now skips its connect work while the element is deferred (only when hydrate support
is loaded: `defer-hydration` is in `observedAttributes`), and finishes it in
`attributeChangedCallback` when `defer-hydration` is removed. Seeded state, init's deferred
commands and `Hydrated` then run as for a top-level component. Tested end to end:
`packages/ssr/test/nested.node.test.ts` writes the server markup and
`nested-hydration.test.ts` hydrates it and clicks the nested child.

## Addendum: CSP

Hydration seeds need no inline-script allowance (`data-gyral-seed` is an attribute; the store
seed is `type="application/json"`, which CSP doesn't execute). Declarative Shadow DOM
`<style>` elements do require `style-src 'unsafe-inline'` (or hashes).

## Addendum: no duplicate state in seeds (gyral-4k7.10, 2026-10-04)

Components often derive state from props (`init: (p) => ({ items: p.items })`), so seeds used
to carry the same data twice. The server now omits `state` from a seed when it serializes
exactly like `init(props)` for the same props (`{"props":{…}}`); the client recomputes it with
`init`, which must be pure (it always had to be: hydration renders `init`'s view). State
changed by `initialMessages` or reducers differs from `init`'s and is still seeded. A
200-item list now seeds once instead of twice (`render.node.test.ts`).

## Addendum: JSON safety check for seeds (gyral-4k7.5, 2026-10-04)

Everything a seed carries must survive `JSON.stringify` → `JSON.parse` unchanged, or the client
hydrates from different data than the server rendered. While writing a component seed, a page
store seed or a `<gyral-stores>` seed, the server checks the value (`jsonHazard`) and warns once
with the first offending path:

`<shop-listing>: seed.state.updated is a Date (becomes a string), so the client would hydrate…`

The check reports non-finite numbers, `undefined` in arrays, functions, symbols, bigints,
`Date`s, `Map`/`Set`/class instances (anything not a plain object or array) and cycles.
`undefined` object properties are allowed: they vanish, and reading them still gives
`undefined`. It runs only on the server, where seeds are written, and costs one walk per seed.

## Addendum: global styles in `page()` (gyral-4k7.7, 2026-10-04)

`page({ styles })` takes the app's global CSS (a string or an array of strings, typically a
`?raw` import of the app stylesheet) and writes one `<style>` element per entry in the head, so
apps no longer import `unsafeHTML` for it. A `</style` sequence inside the CSS is written as
`<\/style` (the same text to CSS), so the element can't be closed early. It is for trusted,
app-authored CSS; never user input.

## Addendum: empty text parts after hydration (gyral-4k7.12, 2026-10-04)

A text binding whose server value is an empty primitive (`''`, `null`, `undefined`) renders as
`<!--lit-part--><!--/lit-part-->` with no Text node in between. Lit's client hydration still
records the primitive as the part's committed value
(`@lit-labs/ssr-client/development/lib/hydrate-lit-html.js:182-184`), and the next text commit
assumes `_$startNode.nextSibling` is a Text node and sets its `.data`
(`lit-html/development/lit-html.js:952-968`), so the text lands inside the closing
`<!--/lit-part-->` comment and never shows (found by gyral-shop checkout).

**Fix:** after a server-rendered Gyral element's first (hydrating) update, `define()` calls
`fillEmptyTextParts(renderRoot)`, which inserts an empty Text node between every
`lit-part`/`/lit-part` pair with nothing in between: the DOM a client render would have
produced. Harmless for `nothing` and empty iterables (they clear or insert before the end
marker). Nested shadow roots are repaired by their own hosts; hidden light markers are repaired
by the light host when it reveals and hydrates them. Apps no longer need to write `nothing`
instead of `''`. Tests: `ssr/test/empty-text-hydration.test.ts` (shadow and light, cycling
values, closing marker intact).

## Addendum: lazy hydration islands (gyral-4k7.4, 2026-10-04)

`define(tag, { hydrate: 'idle' | 'visible' | 'interaction' })` makes a server-rendered component
hydrate later than page load. The server writes Lit's `defer-hydration` plus
`data-gyral-hydrate="<strategy>"`; on connect the client schedules the release:
`requestIdleCallback` (falling back to a 200 ms timeout where it is missing), an
`IntersectionObserver`, or the first `pointerover`/`pointerdown`/`focusin`/`touchstart` on the
host. Those arrive before the click, so the first click on an `interaction` island still
lands. Releasing removes `defer-hydration`, Lit's hydrate support hydrates in place (DOM
identity kept) and `define()` finishes connecting (the nested-components fix above). Stores and
nested Gyral children work; children inside an island hydrate when it does. Until release the
island is inert server HTML (links and forms still work without JS). `load` (default) and
client-only renders are unaffected. Limitation: an island nested inside another component's
server-rendered shadow root is released by that parent's hydration (Lit removes
`defer-hydration` during its walk), so islands belong at page level. `@gyral/testing`'s
`hydrated()` skips elements still under `defer-hydration`. Tests:
`ssr/test/islands.node.test.ts`, `ssr/test/islands-hydration.test.ts`.

## Addendum: `<textarea>` (gyral-czi.34, 2026-10-04)

Lit cannot bind inside `<textarea>` (raw-text content): `` html`<textarea>${v}</textarea>` `` fails during SSR ("Unexpected final partIndex") and never updates in the browser. Use `textarea({ value, attrs })` in a child position instead. It renders the element as a static,
escaped template (correct no-JS markup that hydrates in place), then keeps the same element in
sync: attributes on every update,`value`only when the model's value changes, so text typed
before hydration, or not yet sent through an intent, is never clobbered. Attribute names are
validated and values escaped. Tests:`packages/ssr/test/textarea*.test.ts`.

## Addendum: hydration must not depend on module evaluation order (gyral-czi.41, 2026-10-05)

**Bug.** gyral-shop's production build rendered every server-rendered shadow root twice (two
`<header>`s, two cart `<h1>`s) and threw "Hydration value mismatch" on light-DOM pages
("Primitive found where TemplateResult expected" in the listing, "Unexpected TemplateResult
rendered to part" in the light header). Development builds and every test were clean.

**Confirmed cause: evaluation order, not Lit's production code.**

- Lit's hydrate support only takes effect if `globalThis.litElementHydrateSupport` is defined
  when `lit-element` evaluates: `lit-element` calls it once, at module evaluation
  (`lit-element/development/lit-element.js:200`; production `lit-element.js:6`,
  `s.litElementHydrateSupport?.({LitElement:i})`).
- The shop's client entry uses top-level `await` around lazy component imports. A lazy chunk
  cannot import from an entry that awaits it, so Rolldown moves the shared modules (Lit, Gyral
  core) into a separate chunk (`define-*.js`), which the entry imports and therefore evaluates
  first. `@gyral/ssr/hydrate` (and with it `lit-element-hydrate-support.js`) stays in the entry
  chunk's own body, which runs after. Result: LitElement was never patched in production.
- Without the patch, `ReactiveElement.createRenderRoot` reuses the declarative shadow root and
  LitElement renders into it with `renderBefore` = its first child, prepending a second copy of
  the view. And `defer-hydration` stops meaning anything (the patch is what adds it to
  `observedAttributes` and holds back `connectedCallback`), so nested children hydrated before
  their parents: a light child revealed its markers inside its light parent, and the parent's
  hydrate walk then met them (the two mismatch messages).
- Native ESM in development keeps source order, so the bug only appears in bundled builds.

**Fix (Gyral no longer relies on Lit's patch for its own components).**

- `define()` reuses a declarative shadow root in its own `createRenderRoot` and hydrates it on
  the first update with Lit's public `hydrate()` (registered by `@gyral/ssr/hydrate`), exactly
  as light hosts already did (ADR 0014). Lit's later `render()` then updates the part in place.
  Without `@gyral/ssr/hydrate` it clears the server view and renders fresh (styles adopted).
- Gyral components always observe `defer-hydration`. If Lit's patch is not installed (it adds an
  own static `observedAttributes` to LitElement), Gyral holds back `LitElement.connectedCallback`
  itself until the attribute is removed (by the parent's `hydrate()` walk or an island). If the
  patch is installed, behaviour is unchanged.
- Raw `LitElement` components (not `define()`) still need Lit's patch installed before Lit
  evaluates; for code-split builds set Rolldown's `output.strictExecutionOrder`, or load
  `@gyral/ssr/hydrate` from its own `<script type="module">` before the app entry.

**Guards.**

- `packages/ssr/test/late-support-hydration.test.ts` and `late-support-light-hydration.test.ts`
  import Lit before `@gyral/ssr/hydrate` (the bundler's order) and run in both the development
  and production-Lit browser projects; they fail without the fix (duplicated shadow view; light
  children recreated, light-in-shadow child not hydrated).
- `pnpm smoke:prod` builds the SSR examples for production and compares each page's server view
  with the hydrated one (page errors, `<h1>` count, top-level elements per component).
  `examples/isomorphic` now lazy-loads a light component with top-level `await`, the shape that
  triggered the bug; with the old code the smoke test reports the doubled view.

## Addendum: Gyral's own server renderer (gyral-g1r.9, 2026-10-06)

`@gyral/ssr` renders with `@gyral/core/server` (view/06-server.md); Lit SSR is gone. Changes in
behaviour, all specified in view/06:

- `serverHtml` is removed: page shells and `head` content are core's `html`.
- Seeds are single-quoted (`data-gyral-seed='{"props":{}}'`), escaping only `&` and `'`. The
  JSON-hazard check runs in development only.
- Nested components are no longer deferred: only islands get `defer-hydration`, and islands
  may sit anywhere (the "islands belong at page level" limitation goes with Phase 5's
  hydration).
- The CSP addendum above is superseded: DSD `<style>` elements are allowed by hash
  (`contentSecurityPolicy()` → `renderPage({ csp })`), no `'unsafe-inline'`.
- `invalid()` writes `aria-invalid` on the server (its server half), so it is no longer
  written twice by views.

## Addendum: hydration in core (gyral-g1r.10, 2026-10-06)

Hydration is Gyral's own (view/07-hydration.md); the Lit hydrate support is gone,
`@gyral/ssr/hydrate` is an empty entry kept only so 0.2 imports still resolve, and the workarounds above (evaluation order, mangled private fields,
`fillEmptyTextParts`, `liveBoolean`, `textarea()`, holding back `connectedCallback`) have no
successor. Changes in behaviour:

- **Each component hydrates on its own**, parents first within a flush only for ordering. A
  parent's walk adopts a nested host and its slotted children but never the child's shadow
  root or a light child's content, so neither order can break the other.
- **Islands anywhere:** an island nested in a hydrated component keeps `defer-hydration`
  until its own trigger. The reverse changed: a component inside a pending island hydrates
  at load (it is connected); only the island waits. The "children inside an island hydrate
  when it does" behaviour above no longer holds.
- **Decision 3 holds:** `Hydrated`, then `init`'s commands, after the hydrating render
  (post-render queue, view/04).
- **Mismatches** are explicit: `HydrationMismatch` in development (logged by the scheduler
  with tag, template location, DOM path, expected and found); in production the one host is
  cleared and rendered fresh with a warning. Form state the user changed before scripts ran is
  kept until the model changes it.
- A seeded host with an empty root (no DSD) renders fresh; a DSD without a seed is cleared.
